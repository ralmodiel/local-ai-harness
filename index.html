The short version#

A mini PC and two external GPUs from a hardware stash give five chips: the Ryzen CPU runs the scripts the models write, and the other four each run a local AI model. More than 30 models from a dozen labs, and seven inference engines (see Engines compared), competed for them on the same tests. Here is who won each chip and why; every number is backed by the full results further down.

Terms used on this page
  • tok/s: tokens per second, the speed of the output (a token is about three-quarters of a word).
  • Prompt reading vs writing (pp / tg): pp = reading the prompt, tg = writing the answer; pp512 / tg128 = a 512-token prompt and 128 written tokens.
  • MoE (mixture of experts): a model split into many "experts", only a few of which run per token, so a big model is cheap to run.
  • Expert offload (-ncmoe N): keeps the experts of N layers in system RAM instead of GPU memory, so models bigger than the GPU still run.
  • Speculative decoding (MTP, DFlash, EAGLE3): a small helper guesses the next tokens and the main model checks them: faster output, same result.
  • Quantization (Q4_K_XL, IQ2_XS, IQ3_XXS…): storing weights in fewer bits to shrink a model; the number is roughly bits per weight.
  • GSQ-RCO: a compression method from IST Austria used for several builds here; the "Coder" build also drops half the experts, chosen for code.
  • Thinking budget / effort: a cap on how many reasoning tokens a model may spend before answering; "low" and "xhigh" are effort presets.
  • Seeded bugs (24- and 80-item sets): bugs deliberately planted in the app's real code; the score is the share found.
  • Mutation killing: unit tests must pass on the real code and fail on deliberately broken copies.
  • eGPU / OCuLink / USB4: external GPU connections; OCuLink here is a PCIe 4.0 x4 link, a quarter of a desktop x16 slot.
  • Tiers: fast (NVIDIA card), best (iGPU), third opinion (RX 7600), deep (the strongest reviewer, swapped onto the NVIDIA card on demand).

Memory budget, bandwidth and goals

Memory available to the tests. 64 GB installed doesn't mean 64 GB usable:

GiB
Installed (SO-DIMM) 64.0
Reserved for the iGPU frame buffer (UMA carve-out, set in BIOS) −2.0
Firmware and kernel reservations about −2.6
Seen by the OS 59.4
Docker app stack running alongside (10 containers, idle) about −0.2
AMD-tier Qwen Q4 when loaded (lives in system RAM via GTT) about −22

Notes:

  • Docker isn't the cause: idle containers barely register. The big competitor is the AMD-tier model, because an iGPU's "VRAM" is ordinary system RAM. It was stopped to free about 22 GB (leaving roughly 55–57 GiB) for the GLM-5.3-Flash -ncmoe sweeps and evals, and for the 44 GB GLM-5.2 run. The other GLM-5.2 runs (CPU, and CUDA with 28 GB) had it loaded.
  • Lowering the carve-out: setting the UMA frame buffer to its BIOS minimum would recover up to about 2 GiB. The iGPU allocates through GTT anyway.

Memory speed.

  • Older and slower than the platform's limit: the modules are DDR5-4800. The amdgpu driver's top memory clock is 2400 MHz (DDR: 4800 MT/s), and the kernel detects DDR5 SPD hubs on both SO-DIMMs. The HX 470 supports DDR5-5600 on SO-DIMMs.
  • Theoretical peak: 2 channels × 8 bytes × 4800 MT/s = 76.8 GB/s.
  • Measured (STREAM-style triad, 24 threads): about 48-49 GB/s idle (copy ~43 GB/s; same at 8, 12 and 24 threads), about 63% of the 76.8 GB/s theoretical; 47 GB/s with a RAM-offloaded model running.
  • Why it matters: RAM bandwidth caps every run that keeps model weights or experts in system RAM: the AMD iGPU tier, the CPU parts of MoE offload, and GLM. For example, GLM-5.3-Flash at IQ2 reads several GB of experts per token. DDR5-5600 would add about 17% bandwidth; LPDDR5X-8000 machines (Ryzen AI Max) have about 3× more.

Goal: offload bulk, low-stakes coding work on a real production web app: extraction, first-pass review, drafts, screenshot triage from Claude to local models, measured for both speed and quality of output.

Exploration window: 2026-10-15 to 2026-10-19 (new hardware from the evening of 2026-10-18).

The full test suite and scoring

How models are compared:

  • An eval script runs project-grounded tasks, each auto-scored from 0 to 1, with no Claude tokens spent judging.
  • Inputs come from the app's source, pinned at one fixed commit so scores stay comparable across days.
  • A matrix script runs a list of configs unattended, one after another.
  • The tables below are regenerated by a report script after every batch.
Category Task Scoring

Settings that matter: thinking budgets, speculative decoding, quantization bits

Effort levels: bounded thinking helps; unbounded or tiny budgets hurt. On the 80-item set:

model thinking off budget 256 budget 1,024 unbounded
Gemma 4 26B (NVIDIA) 0.875 (1.5 min) 0.713 0.912 (10 min) 0.05 (runs out at 4K)
Qwen3.6 Q4 (iGPU) 0.887 (7 min) 0.850 0.912 (57 min) 0.800 (2.5 h)
  • A request can set the budget itself with "thinking_budget_tokens": N (llama.cpp; the server-wide equivalent is --reasoning-budget N).
  • The harness exposes this as local_ask effort="high", which means thinking capped at 1,024 tokens.

Unbounded thinking hurts, and more bits don't help. On the 80-item set:

  • Thinking takes the iGPU model from 0.887 to 0.800, and from 7 min to 2.5 h.
  • Gemma's thinking over-deliberates until it hits the token budget, scoring 0.05 at 4K tokens; that's not a parser bug.
  • On the iGPU, Q5_K_S and MXFP4_MOE both score 0.875 against 0.887 for Q4_K_XL: quality saturates at 4-bit.
  • Gemma's MTP draft length is best at the default 3 (171 / 161 / 189 tok/s on code, summary and JSON). Longer drafts only pay on JSON.

MTP speculative decoding is the biggest win, and it's in production. The Unsloth Qwen3.6-35B-A3B-MTP-GGUF running with --spec-type draft-mtp decodes at about 196 tok/s against 104 without it. Draft acceptance runs 70–92%, at the same or better quality (0.879 → 0.919 on the easy suite).

  • The MTP head costs VRAM, so llm-nv-main now runs 2 slots × 32K, and the vision encoder runs on the CPU (--no-mmproj-offload). An image still takes about 9 s.
  • On the GPU, the vision encoder hit OOM at every context size tried, down to 40K.
  • 99% of real prompts are under 7K tokens (from the router's usage log). The router now skips a backend when a prompt exceeds its max_prompt, so prompts over 30K go to the AMD 64K slots.

Newer llama.cpp (b11706, 64 commits later, including a Vulkan KV-cache change for AMD) gave no real gain. On the same prompts and production configs:

  • iGPU: 23.4 tok/s decode on both builds.
  • NVIDIA: 146 tok/s decode on both; prompt reading 2,060 → 2,142 tok/s.
  • Production stays on the proven build.
  • MTP decode speed depends on content (146 tok/s on one prompt, about 196 on the eval tasks), so only compare configs on identical prompts.

ROCm on the 890M is no faster than Vulkan. This used llama.cpp's prebuilt ROCm build with Ubuntu 26.04's packages (sudo apt install libamdhip64-7 libhipblas3 librocblas5).

  • Ubuntu's rocBLAS has no kernels for the 890M's chip (gfx1150). HSA_OVERRIDE_GFX_VERSION=11.0.0 makes it run the gfx1100 kernels.
  • Production shape: 25.0 tok/s decode and 471 tok/s prompt, against Vulkan's 23.4 and 478.
  • Vulkan stays, since it needs no override.

N-gram speculative decoding (ngram-mod) gave no gain on these tasks: the outputs are short and don't copy the input. It may still help whole-file rewrites; not tested yet.

One countdown per chip#

The home setup has five chips. One, the Ryzen CPU, is reserved for running the scripts the models write; the other four each need the right AI model. So: four countdowns (third place, second place, the winner, and why), plus a bonus round for the NVIDIA card's deep mode.

NVIDIA RTX 5060 Ti 16 GB: the fast tier#

  • 3rd place: gpt-oss-20b (OpenAI): 65/80 bugs and 7/9 unit tests, but ~128 tok/s and no vision.
  • 2nd place: Qwen3.6-35B-A3B IQ3 (the old fast tier): just as fast (~196 tok/s) but only 53/80 bugs.
  • Winner: Gemma 4 26B-A4B QAT + MTP: ~200 tok/s, 70/80 bugs (77 with a 2K thinking budget), 7/9 unit tests, reads screenshots.
  • Why: This tier takes lots of small jobs, one after another, so speed decides; Gemma is also the best test writer and reads screens. It beat 10 other models for this job.
Full numbers for the NVIDIA card

The fast tier is now Gemma 4 26B-A4B QAT (UD-Q4_K_XL) with its MTP draft, replacing Qwen3.6-35B-A3B IQ3_XXS.

  • In the production shape (2 × 32K, vision on CPU) it scores higher: 0.894 against about 0.863 over 8 categories.
  • It finds more bugs: bugauto 0.792 against 0.708, and bugspot 1.0 against 0.6.
  • It's faster: on the same 5.5K prompt, 2,138 tok/s prompt against 1,892, at the same decode speed.
  • Vision is as accurate and 2.5× faster: 84 s for 20 pages against 206 s.
  • It loses only on codegen (0.8 against 1.0).
  • 2 × 32K at the default micro-batch loads, then runs out of VRAM on the first real request. -ub 256 fixes it, so test fit with a real long request, not /health.

gpt-oss-20b on the GPU (12.1 GB MXFP4, low effort): close to the fast tier, and as good at unit tests (7 of 9), with very fast prompt reading (~5,000 tok/s); 65 of 80 bugs and ~128 tok/s keep Gemma 4 (70 of 80, ~200 tok/s, plus vision) in the fast tier. Its EAGLE3 drafter added a modest 7% (138 tok/s).

New model: Meta's Muse Glimmer 30B (dense 29.6B with a vision encoder, August 2026, Apache-2.0), as Unsloth's UD-IQ3_XXS (13.1 GB) fully on the 16 GB card. At low reasoning strength it found all 80 of 80 seeded bugs — the first perfect score on this rig — plus 23 of 24 on the smaller set, 21 of 23 scripts and 6 of 9 unit tests (tied with Ornith-1.5-35B for the best of any big model here; Gemma 4 has 7). It always thinks, so it writes at ~30 tok/s, but its DFlash drafter nearly doubles that to ~57 tok/s (70% of drafted tokens accepted, same output). Screen reading 0.931, a step below the current tiers. The strongest bug hunter yet that runs on the GPU alone.

Qwen3.8-27B and its Swift 1.5 tune on the card alone:

  • Swift 1.5 Qwen3.8-27B IQ3_S + MTP (12.1 GB, fully on the 16 GB card, ~52-64 tok/s) on 10 seeded bugs: low effort found 9 of 10 in 7 minutes; the template's default xhigh found 8 in 16 minutes with twice the thinking (44K tokens); thinking off found 8 in 26 seconds. On this kind of bug hunt, xhigh bought nothing — low effort is the sweet spot, and thinking off is the fast path. The template's default really is xhigh.
  • Base Qwen3.8-27B vs Swift 1.5 on the same 10 bugs: at xhigh both found 8, and Swift needed 35% fewer thinking tokens (44K vs 68K; 16 vs 24 minutes) — close to the 42% UkisAI reports. At low effort the base model was the best option of all: 9 of 10 in 4 minutes with only 12K thinking tokens (Swift: 9 of 10, 22K tokens, 7 minutes). Thinking off: 8 of 10 in 26 seconds for both. Takeaway for a 16 GB card: use low effort for bug hunts, xhigh only when you've measured it helps, and Swift if you do run xhigh.
  • Swift 1.5 Qwen3.8-27B IQ3_XXS + MTP (10.4 GB) fits entirely on the 16 GB card with a 64K context: it found 12 of 12 functions in a 56K-token prompt in 83 seconds (reading at ~715 tok/s, writing at ~50 tok/s), and matched the larger IQ3_S on the bug sets (8 of 10 at xhigh and with thinking off). A strong long-context option that needs no RAM offload.
  • Full test suite, Swift 1.5 27B IQ3_XXS (10.4 GB, entirely on the 16 GB card, with vision): at low thinking effort it found 24 of 24 and 78 of 80 seeded bugs and wrote 22 of 23 scripts — matching the best scores on this rig (the 68 GB Flash-Next deep tier models need system RAM for the same scores), at ~64 tok/s instead of ~24. Screen reading 0.965, level with the current tiers. Thinking off it is quick and solid (0.840 suite, 72 of 80 bugs). Its one weak spot is writing unit tests (2.5 of 9), where the fast tier stays ahead (7). That run of 104 tasks took 38 minutes, so it suits careful review work rather than quick jobs.
  • Same test, base Qwen3.8-27B IQ3_XXS at low effort: 23 of 24 and 78 of 80 bugs, 23 of 23 scripts, in 39 minutes with about the same thinking (129K vs 127K tokens). So the jump comes from switching low-effort thinking on, not from the Swift fine-tune: any Qwen3.8-27B at IQ3_XXS gives a 16 GB card deep-tier accuracy at ~63 tok/s with no system RAM. Swift's edge shows at xhigh, where it thinks 35% less.
  • Community build of the same quant — kunthawat's Swift 1.5 27B IQ3_XXS (10.2 GB, Unsloth-style imatrix): as good as UkisAI's own file and a little better without thinking: 0.858 vs 0.840 on the suite, 74 vs 72 of 80 bugs, 22 vs 19 scripts. At low effort it found 23 of 24 and 78 of 80 with 23% less thinking (98K vs 127K tokens, 31 vs 38 minutes). Its author's 16 GB profile (one slot, 100K context, 4-bit KV cache) really fits: it found 12 of 12 functions in an 82K-token prompt in 2 minutes, all on the GPU.

Qwen3.8-27B now fits the fast tier's shape. IST Austria's GSQ-RCO IQ3_S with MTP built in (12.1 GB) serves 2 × 32K with the vision encoder on the CPU (-ub 256), and a real 26K-token prompt ran (read at 860 tok/s). Against Gemma 4: more bugs (0.925 against 0.875 on the 80-item set, 21 against 19 of 24), one more script (20), the same screenshot score (0.965, but 204 s against 84 s), far fewer test tasks (2 against 7 of 9), and about 60 tok/s against 200. It's a candidate for a switchable review mode, not the default.

Qwen3-Coder-30B-A3B (UD-Q3_K_XL) loses to Gemma 4 on every category we use (bugs 0.738 vs 0.875, scripts 17 vs 21, tests 3 vs 7) at half the decode speed (~106 tok/s).

LFM2.5-24B-A2B: rejected. It always reasons; neither enable_thinking=false nor reasoning_effort=low stops it, so at a normal token budget it never answers.

  • With a 3000-token budget it scores 0.591, finds almost no bugs, and wrote 134K tokens for the suite.

Unit-test writing, scored by mutation killing. The model writes bun:test tests for 9 pure functions from the app. The tests must pass on the real code and fail on deliberately broken copies (15 mutants, after dropping one equivalent mutant a frontier model's tests also couldn't kill).

  • Gemma 4 (fast tier): 7 of 9 functions in 67 s, killing every mutant wherever its tests passed. Qwen3.6 Q4 on the iGPU: 3 of 9, in 680 s.
  • Every miss was a test with a wrong expectation, so it fails on the correct code. A real run can detect that without a reference answer, so execute-and-repair should recover most of these.

Radeon 890M iGPU: the best tier#

  • 3rd place: Ornith-1.5-35B (Ornith AI): 61/80 bugs at ~12 tok/s.
  • 2nd place: MiniCPM-V 4.7 (OpenBMB): built for images, but read screens less accurately (0.939) and isn't a code reviewer.
  • Winner: Qwen3.6-35B-A3B Q4_K_XL + MTP: 71/80 bugs, screen reading 0.968 (tied best), ~25 tok/s.
  • Why: The strongest reviewer that fits this chip, and the best screen reader; it takes the jobs where being right matters more than being fast. It beat 3 other models for this job.
Full numbers for the iGPU

Long prompts cost speed, not accuracy, on the iGPU tier. A probe packs real source files into one prompt and asks which file defines each of 12 functions spread through it. Qwen3.6 Q4 on the iGPU (64K slots) found all 12 at 18K tokens (prompt read at 357 tok/s, 84 s in all) and at 55K tokens (187 tok/s, 3.6 min).

Ornith-1.5-35B-A3B (a Qwen3.5-MoE fine-tune) doesn't beat the current tiers. On the 5060 Ti (IQ3_XXS) it scores 0.723 without thinking; with a 2,048-token thinking budget it finds 0.887 of the 80 bugs and passes 19 scripts and 6 test tasks at 113 tok/s, close to Gemma 4 but not better (0.963 bugs, 21 scripts, 7 tests at max effort). On the iGPU (Q4_K_M) it scores 0.776 at 12 tok/s, against Qwen3.6's 0.878 at 22. Llama 3.1 8B, Mistral Nemo 12B and Ling 3.0 Tiny score 0.52–0.60; both DeepSeek-R1 distills are worse still (0.37–0.46) and slow.

Vision (local Qwen3.6 multimodal) for UI audits#

  • Triage only: about 30% of its UI findings were confirmed by deterministic probes (DOM measurement, axe).
  • No exact numbers: pixel and contrast claims from the model are filtered out in code, because scripts measure those.

Why none was selected:

  • Its answers scored lower than the same model on llama.cpp, on every model: 1–5 fewer of the 80 seeded bugs, and lower code and script scores. A model is the file; an engine is the program that runs it. The same file can run noticeably faster or slower depending on the engine, and occasionally score differently, so engines got the same treatment as models: same file, same prompts, speed and answers measured.

What this shows:

  • On NVIDIA, use llama.cpp's CUDA build; on AMD GPUs, the Vulkan build is the simple, fast default (ROCm adds setup for little or no gain here).
  • Wrappers cost little once loaded. Ollama runs at llama.cpp's speed, so pick it for convenience and llama.cpp for control (exact flags, drafters, multiple GPUs).
  • The newer engines are genuinely faster in their niche: Strata for MoE models bigger than the card, Magnitude for small models that fit. Always re-run the quality tests too: Strata's speed came with a few more missed bugs.
  • Speculative drafting is the biggest single speed lever, in any engine: DFlash took the RX 7600 from ~38 to ~95 tok/s.

Not tried yet (popular, but outside this box's sweet spot or still on the list):

  • ik_llama.cpp: a llama.cpp fork tuned for CPU+GPU splits of big MoE models; a natural next test for the RAM-offloaded runs.
  • vLLM and SGLang: built for serving many users at once from models that fit fully in VRAM; a single user on 16 GB gains little.
  • ExLlamaV3: fast NVIDIA-only engine with its own quant format; worth a look for the fast tier.
  • LM Studio, Lemonade, GAIA: friendly apps on top of llama.cpp and FastFlowLM, so expect their engines' speeds.
  • KTransformers: CPU+GPU hybrid for very large MoE models.

Where local AI pays off#

Where the local tiers shine (measured overnight, 2026-10-19/20, inside real QA work): Claude teammates handed specific jobs to the local models and checked every answer against a known result.

  • Turning a confirmed bug into a runnable repro script. For 17 bugs Claude had confirmed, the 5060 Ti's Gemma 4 wrote bash + curl scripts that all reproduced the bug; 8 ran as-is, the rest needed a small fix (a stray quote, a mistyped id). Seconds per script, no Claude usage for the drafting. Read each one before running it: one draft appended a clean-up rm -rf of the working folder.
  • Finding the real error in a wall of logs. Given a 4–14 KB stack trace or server log, Gemma 4 named the actual root cause and the right stack frame 3 of 3 times in 1–5 s (it occasionally misquotes a line number).
  • Reading a screen. In a plain-transcription mode, Qwen3.6's vision read about 100 labels, dates and numbers across the app's pages exactly, inventing nothing and missing nothing, in 11–15 s per screenshot.
  • Drafting regression checks for fixed bugs. For 11 fixes, the local model drafted a check for each in seconds; 5 were right as drafted and the rest were a fast starting point for Claude to harden (it sometimes invents endpoints, so give it the source file). The result is a committed regression runner: 15 suites that re-check every fix in about a minute.
  • Mapping who can call what. Asked to list every HTTP endpoint and its allowed roles from a backend source file, Qwen3.6 on the iGPU got 118 of 118 endpoints right across the night's reviews (class-level defaults and per-method overrides included), inventing nothing, in 5–75 s per file. A cheap access-control matrix for every review.
  • "Where is the code that does X?" Local semantic search put the right file in its top 4 results for 14 of 15 plain-English questions, in about half a second once the index is warm.
  • Checkable number crunching. The local model writes a script, a second model writes its own independently, and the answer counts only when both agree. Across 12 jobs on real exported data (report totals, mean / standard deviation for 54 groups, group averages, category counts, multi-table joins), every answer marked VERIFIED was right: 11 of 11. The one job too intricate for the local models (a multi-step classification rule) came back as a disagreement instead of a wrong number, which is exactly when Claude should take over. (Harness fixes made this work: the sandbox now sees exported files and folders outside the repo, correct output is no longer rejected for not being strict JSON, and two scripts that agree on an empty answer are reported as EMPTY instead of VERIFIED.)

  • Still not worth it: judging UI design from screenshots, as opposed to reading them (about a quarter of the critique claims were wrong) and copy-editing UI text (about 1 in 5 flags was real). Next: more of the verification legwork (repros, role matrices, number checks) moves to the local chips, so Claude spends its usage on deciding what's wrong.

  • So far the local tiers pay off on bulk, checkable work (scripts, extraction, screenshot triage, cross-checks), not on finding subtle bugs in real code.

  • The cheapest win wasn't a model at all: small deterministic tools that bound command output (a code outliner, grouped search, test/log/diff/JSON summarizers). Replayed on the commands of 95 past agent sessions they kept 100% of what mattered (96.7% for JSON) and cut the output 3–40× (outline 2.6×, search 4.2×, test output 30×, logs 30×, diffs 39×), so the frontier model reads far less.
  • One QA round aimed the local tiers at their strengths. Screenshot triage: the local vision model pre-screened 14 of 16 screenshots, so the reviewer opened one; one of its leads was confirmed (a phone layout pushing a data grid below the fold), the rest were cosmetic or wrong.

  • it keeps useful scripts for reuse.

GLM-5.2 on Colibri, rerun on the fast SSD: 0.31 → 0.50 tok/s, still unusable. Best cold setup: CUDA, model on the Samsung, a 248 GB partial mirror of the most-used experts on the WD (COLI_MODEL_MIRROR), direct reads and pipelined loading (DIRECT=1 PIPE=1); 28% of expert bytes came from the mirror. Patches and workarounds that were needed:

  1. Driver mismatch after installing utils. Installing nvidia-utils-595-server removed the 580 kernel modules. The fix was installing the matching nvidia-driver-595-server-open.
  2. OCuLink eGPU isn't hot-pluggable. Power the dock before a cold boot, or the card isn't on the PCIe bus.
  3. CUDA runtime for the llama.cpp CUDA build. The prebuilt binary needs libcudart.so.12, libcublas.so.12 and libcublasLt.so.12. These were copied from NVIDIA's cudart and cuBLAS redistributables into the binary directory, and units set LD_LIBRARY_PATH to it. - Copying the libraries while the tarball was still extracting caused a bus error. Copy only after extraction completes.
  4. Driver 595 ships CUDA 13.x, but the llama.cpp build is CUDA 12.8. It works through the driver's forward compatibility, and Blackwell (sm_120) is supported.
  5. Vulkan picks the wrong GPU when the eGPU is attached. Pin the Radeon by pointing VK_DRIVER_FILES at the RADV ICD file. On 26.04 it's named radeon_icd.json, not radeon_icd.x86_64.json.
  6. ROCm/HIP vs Vulkan: Vulkan (RADV) is faster than ROCm on the 890M (gfx1150), as reported in llama.cpp #20099, so ROCm isn't installed.
  7. Playwright refuses Ubuntu 26.04. Install the browsers with: PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64 npx playwright install chromium-headless-shell chromium Screenshots and UI audits depend on this.
  8. Running sudo from an AI agent: sudo can't prompt for a password through the agent's shell. Run privileged steps in a separate SSH session: - the driver - the CUDA repo and toolkit - libvulkan-dev and glslc (needed for Colibri's Vulkan build) - linger
  9. The NPU needs one root step. Install Ubuntu's libxrt2/libxrt-npu2 plus FastFlowLM's .deb, and raise memlock to unlimited (see the NPU section). No PPA or DKMS on Ubuntu 26.04 with kernel 7.0.
  10. Colibri's start-here.sh auto-starts a server on :8000 after downloading. Stop it before starting the managed llm-deep unit.

Build and ops gotchas#

  • Two llama.cpp builds live side by side:
  • Vulkan, for AMD.
  • CUDA 12.8, for NVIDIA, with the cudart libraries copied in.
  • Bus error in the CUDA build: caused by copying the cudart libraries while the tarball was still extracting. Copy only after extraction finishes.
  • Vulkan device choice: with the eGPU attached, Vulkan must be pinned to the Radeon with VK_DRIVER_FILES (the RADV ICD file).
  • OCuLink eGPU isn't hot-pluggable: cold-boot with the dock already powered.
  • MCP server edits: a syntax error in the MCP server once made /mcp reconnect fail silently. A smoke test (handshake plus tools/list) now runs before every harness commit.
