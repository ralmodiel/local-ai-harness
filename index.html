A mini PC, two eGPUs and an NPU from a hardware stash do the bulk of real coding work locally, while Claude Code orchestrates (plans, delegates, verifies, makes the final calls), so Claude usage goes to the work that needs it

Today's setup:

  • Gemma 4 on the NVIDIA card for bulk work, scripts and test writing.
  • Qwen3.6 4-bit on the iGPU for reviews and screenshots.
  • Both together, with a capped thinking budget, for bug hunts. A third opinion from Ornith-1.5-9B on the RX 7600 (thinking capped at 1,024 tokens, its own always-on service since 2026-10-19) joins them in a three-model mode: all three answer a real commit review in about 40 s.
  • Qwen3.8-Flash-Next (the pruned GSQ-RCO Coder build) as the deep tier, swapped onto the NVIDIA card on demand: reviews whole commits in about a minute and reads 64K-token prompts. Its unprompted bug claims about a single file need checking. It replaced GLM-5.3-Flash, which matched its scores at a fifth of the speed and never finished a diff review; GLM's files are deleted.
  • Diff reviews now get the commit messages along with the diff. Without them, every model reported the commit's intended changes as regressions.
  • The NPU stays idle in production: its best model (Qwen3.6-35B) is weaker and slower than the GPU tiers and would pin 22 GB of RAM next to the app stack.

Latest model test — Swift 1.5 (2026-10-20, running overnight): UkisAI's Swift 1.5 builds of the same models, tuned to think less at the same quality.

  • Swift 1.5 Qwen3.8-Flash-Next GSQ-RCO IQ2_XS (68 GB, experts in RAM, -ncmoe 36 on the 16 GB card): 24 of 24 seeded bugs with thinking off, in 5.8 minutes — the best score measured on this rig (the current Coder deep tier: 22 of 24; the old GLM tier needed 26 minutes for 24). On the 80-item set it scored 0.975 (78 of 80), tying the best result on this rig (Coder deep tier: 0.963). It was slower here (31 min, ~5.5 tok/s) but measured while other model downloads were writing to the same SSD the experts stream from; a clean speed run follows, with a thinking-on run and three larger quants.

Where the local tiers shine (measured overnight, 2026-10-19/20, inside real QA work): Claude teammates handed specific jobs to the local models and checked every answer against a known result.

  • Turning a confirmed bug into a runnable repro script. For 17 bugs Claude had confirmed, the 5060 Ti's Gemma 4 wrote bash + curl scripts that all reproduced the bug; 8 ran as-is, the rest needed a small fix (a stray quote, a mistyped id). Seconds per script, zero Claude tokens for the drafting. Read each one before running it: one draft appended a clean-up rm -rf of the working folder.
  • Finding the real error in a wall of logs. Given a 4–14 KB stack trace or server log, Gemma 4 named the actual root cause and the right stack frame 3 of 3 times in 1–5 s (it occasionally misquotes a line number).
  • Reading a screen. In a plain-transcription mode, Qwen3.6's vision read about 71 labels, dates and numbers across 6 app pages exactly, inventing nothing and missing nothing, in 11–15 s per screenshot.
  • Drafting regression checks for fixed bugs. For 11 fixes, the local model drafted a check for each in seconds; 5 were right as drafted and the rest were a fast starting point for Claude to harden (it sometimes invents endpoints, so give it the source file). The result is a committed 12-assertion regression suite that re-runs in seconds.
  • Mapping who can call what. Asked to list every HTTP endpoint and its allowed roles from a backend source file, Qwen3.6 on the iGPU got 75 of 75 endpoints right across 9 files (class-level defaults and per-method overrides included), inventing nothing, in 5–75 s per file. A cheap access-control matrix for every review.
  • "Where is the code that does X?" Local semantic search put the right file in its top 4 results for 11 of 11 plain-English questions, in about half a second once the index is warm.
  • Checkable number crunching. The local model writes a script, a second model writes its own independently, and the answer counts only when both agree. Across 9 jobs on real exported data (report totals, mean / standard deviation for 54 groups, group averages, category counts, multi-table joins), every answer marked VERIFIED was right: 8 of 8. The one job too intricate for the local models (a multi-step classification rule) came back as a disagreement instead of a wrong number, which is exactly when Claude should take over. (Two harness fixes made this work: the sandbox now sees exported files outside the repo, and correct output is no longer rejected for not being strict JSON.)
  • Still not worth it: judging UI design from screenshots, as opposed to reading them (about a quarter of the critique claims were wrong) and copy-editing UI text (about 1 in 5 flags was real). Next: more of the verification legwork (repros, role matrices, number checks) moves to the local chips, so Claude spends its usage on deciding what's wrong.

First real QA round with this setup (2026-10-19): two Claude teammates ran discovery on a real production web app (its data pipeline and generated reports checked against the data) with the local tools available, and found 14 verified problems (6 P2).

  • None of the 14 came from a local model. Local first-pass hunts over long service files produced plausible but wrong claims (an authorization hole the resource layer already blocks, a double count a query already prevents); the teammates refuted each one.
  • The one useful local result was a cross-check: a generated script with a second, independent script recomputed a form's totals and confirmed the app's arithmetic (the two scripts disagreed, and the one that matched the API was right).
  • Caveat: the teammates' tool server predated the three-model mode, so they ran the two-model mode. The next round measures the three-model mode and the deep tier's commit pre-review against the Claude reviewer.
  • So far the local tiers pay off on bulk, checkable work (scripts, extraction, screenshot triage, cross-checks), not on finding subtle bugs in real code.
  • The cheapest win wasn't a model at all: small deterministic tools that bound command output (a code outliner, grouped search, test/log/diff/JSON summarizers). Replayed on the commands of 95 past agent sessions they kept 100% of what mattered (96.7% for JSON) and cut the output 3–40× (outline 2.6×, search 4.2×, test output 30×, logs 30×, diffs 39×), so the frontier model reads far less.
  • Round 22 aimed the local tiers at their strengths. Screenshot triage: the local vision model pre-screened 14 of 16 screenshots, so the reviewer opened one; one of its leads was confirmed (a phone layout pushing the grade grid below the fold), the rest were cosmetic or wrong.

Findings (most important first)#

  1. The fast tier is now Gemma 4 26B-A4B QAT (UD-Q4_K_XL) with its MTP draft, replacing Qwen3.6-35B-A3B IQ3_XXS.
    • In the production shape (2 × 32K, vision on CPU) it scores higher: 0.894 against about 0.863 over 8 categories.
    • It finds more bugs: bugauto 0.792 against 0.708, and bugspot 1.0 against 0.6.
    • It's faster: on the same 5.5K prompt, 2,138 tok/s prompt against 1,892, at the same decode speed.
    • Vision is as accurate and 2.5× faster: 84 s for 20 pages against 206 s.
    • It loses only on codegen (0.8 against 1.0).
    • 2 × 32K at the default micro-batch loads, then runs out of VRAM on the first real request. -ub 256 fixes it, so test fit with a real long request, not /health.

  2. Script generation, so analysis runs on the CPU instead of being read by an LLM.

    • The benchmark: 23 tasks, 12 core and 11 hard. The hard ones cover CSV quoting and UTF-8, paths with spaces, date math, joins, multi-line Java annotations, CLI arguments, nearest-rank percentiles, stable ties and a 400k-line stream.
    • How it runs: the model writes a Python or bash script, which runs in a bwrap sandbox (read-only root, no network, prlimit CPU and memory limits) against seeded fixtures. Its output must equal a reference answer.
    • Validation: a frontier model solving the tasks blind from the prompts scores 23/23, so the specs and references are consistent.

Hardware and memory#

Memory available to the tests. 64 GB installed doesn't mean 64 GB usable:

Notes:

  • Docker isn't the cause: idle containers barely register. The big competitor is the AMD-tier model, because an iGPU's "VRAM" is ordinary system RAM. It was stopped to free about 22 GB (leaving roughly 55–57 GiB) for the GLM-5.3-Flash -ncmoe sweeps and evals, and for the 44 GB GLM-5.2 run. The other GLM-5.2 runs (CPU, and CUDA with 28 GB) had it loaded.
  • Lowering the carve-out: setting the UMA frame buffer to its BIOS minimum would recover up to about 2 GiB. The iGPU allocates through GTT anyway.

Memory speed.

  • Older and slower than the platform's limit: the modules are DDR5-4800. The amdgpu driver's top memory clock is 2400 MHz (DDR: 4800 MT/s), and the kernel detects DDR5 SPD hubs on both SO-DIMMs. The HX 470 supports DDR5-5600 on SO-DIMMs.
  • Theoretical peak: 2 channels × 8 bytes × 4800 MT/s = 76.8 GB/s.
  • Measured (STREAM-style triad, 24 threads): about 48-49 GB/s idle (copy ~43 GB/s; same at 8, 12 and 24 threads), about 63% of the 76.8 GB/s theoretical; 47 GB/s with a RAM-offloaded model running.
  • Why it matters: RAM bandwidth caps every run that keeps model weights or experts in system RAM: the AMD iGPU tier, the CPU parts of MoE offload, and GLM. For example, GLM-5.3-Flash at IQ2 reads several GB of experts per token. DDR5-5600 would add about 17% bandwidth; LPDDR5X-8000 machines (Ryzen AI Max) have about 3× more.

Goal: offload bulk, low-stakes coding work on a real web app (React + Java/JAX-RS): extraction, first-pass review, drafts, screenshot triage from Claude to local models, measured for both speed and quality of output.

Exploration window: 2026-10-15 to 2026-10-19 (new hardware from the evening of 2026-10-18).

How models are compared#

How models are compared:

  • An eval script runs project-grounded tasks, each auto-scored from 0 to 1, with no Claude tokens spent judging.
  • Inputs come from the app's source, pinned at one fixed commit so scores stay comparable across days.
  • A matrix script runs a list of configs unattended, one after another.
  • The tables below are regenerated by a report script after every batch.

Patches and workarounds that were needed:

  1. Driver mismatch after installing utils. Installing nvidia-utils-595-server removed the 580 kernel modules. The fix was installing the matching nvidia-driver-595-server-open.
  2. OCuLink eGPU isn't hot-pluggable. Power the dock before a cold boot, or the card isn't on the PCIe bus.
  3. CUDA runtime for the llama.cpp CUDA build. The prebuilt binary needs libcudart.so.12, libcublas.so.12 and libcublasLt.so.12. These were copied from NVIDIA's cudart and cuBLAS redistributables into the binary directory, and units set LD_LIBRARY_PATH to it. - Copying the libraries while the tarball was still extracting caused a bus error. Copy only after extraction completes.
  4. Driver 595 ships CUDA 13.x, but the llama.cpp build is CUDA 12.8. It works through the driver's forward compatibility, and Blackwell (sm_120) is supported.
  5. Vulkan picks the wrong GPU when the eGPU is attached. Pin the Radeon by pointing VK_DRIVER_FILES at the RADV ICD file. On 26.04 it's named radeon_icd.json, not radeon_icd.x86_64.json.
  6. ROCm/HIP vs Vulkan: Vulkan (RADV) is faster than ROCm on the 890M (gfx1150), as reported in llama.cpp #20099, so ROCm isn't installed.
  7. Playwright refuses Ubuntu 26.04. Install the browsers with: PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64 npx playwright install chromium-headless-shell chromium Screenshots and UI audits depend on this.
  8. Running sudo from an AI agent: sudo can't prompt for a password through the agent's shell. Run privileged steps in a separate SSH session: - the driver - the CUDA repo and toolkit - libvulkan-dev and glslc (needed for Colibri's Vulkan build) - linger
  9. The NPU needs one root step. Install Ubuntu's libxrt2/libxrt-npu2 plus FastFlowLM's .deb, and raise memlock to unlimited (see the NPU section). No PPA or DKMS on Ubuntu 26.04 with kernel 7.0.
  10. Colibri's start-here.sh auto-starts a server on :8000 after downloading. Stop it before starting the managed llm-deep unit.

Vision (local Qwen3.6 multimodal) for UI audits#

  • Triage only: about 30% of its UI findings were confirmed by deterministic probes (DOM measurement, axe).

These steps rebuild the local stack on any Ubuntu 24.04 or 26.04 machine with an NVIDIA card (16 GB) and/or an AMD iGPU.

  • $LLM_HOME is any directory you choose (for example export LLM_HOME=$HOME/llm).
  • Everything except step 1 runs as a normal user.

1. System packages (needs sudo; run them in your own terminal, not through an AI agent)#

# NVIDIA driver (open kernel modules). Install the driver package, not just -utils, so the kernel modules match.
sudo apt install nvidia-driver-595-server-open nvidia-utils-595-server
# eGPU over OCuLink/Thunderbolt: power the dock BEFORE booting. OCuLink is not hot-pluggable.

# Vulkan headers + shader compiler (only needed to build Colibri's Vulkan backend)
sudo apt install libvulkan-dev glslc mesa-vulkan-drivers

# CUDA toolkit (only needed to build Colibri's CUDA backend; llama.cpp ships prebuilt CUDA binaries).
# NVIDIA's ubuntu2404 repo also works on 26.04.
wget https://developer.download.nvidia.com/compute/cuda/repos/ubuntu2404/x86_64/cuda-keyring_1.1-1_all.deb
sudo dpkg -i cuda-keyring_1.1-1_all.deb && sudo apt update && sudo apt install cuda-toolkit-13-0

# Let user services start at boot without a login
sudo loginctl enable-linger "$USER"

2. llama.cpp prebuilt binaries (Vulkan for AMD, CUDA for NVIDIA)#

B=b11642; R=https://github.com/ggml-org/llama.cpp/releases/download/$B
mkdir -p $LLM_HOME/bin/vulkan $LLM_HOME/bin/cuda $LLM_HOME/models
curl -L $R/llama-$B-bin-ubuntu-vulkan-x64.tar.gz | tar xz -C $LLM_HOME/bin/vulkan --strip-components=1
curl -L $R/llama-$B-bin-ubuntu-cuda-12.8-x64.tar.gz | tar xz -C $LLM_HOME/bin/cuda --strip-components=1
# The CUDA build needs the CUDA runtime next to it. Extract fully, THEN copy (copying mid-extract caused a bus error).
curl -L $R/cudart-llama-$B-bin-ubuntu-cuda-12.8-x64.tar.gz -o /tmp/cudart.tgz && mkdir -p /tmp/cudart \
  && tar xzf /tmp/cudart.tgz -C /tmp/cudart && cp /tmp/cudart/*/lib*.so* $LLM_HOME/bin/cuda/

Notes:

  • The CUDA 12.8 build runs on the 595 driver (CUDA 13.x) and supports Blackwell (sm_120). A CUDA 13.4 build also exists for this release; it wasn't tested here.
  • On AMD, use Vulkan (RADV), not ROCm. ROCm is slower on the 890M (llama.cpp #20099).

4. Servers (systemd user units)#

Set Environment=LLM_HOME= to your directory in each unit; systemd expands ${LLM_HOME} in ExecStart only from Environment= lines.

Fast tier, NVIDIA 16 GB: Qwen3.6 with MTP speculative decoding (~196 tok/s), with vision.

# ~/.config/systemd/user/llm-nv.service
[Service]
Environment=LLM_HOME=/opt/llm
Environment=LD_LIBRARY_PATH=/opt/llm/bin/cuda
ExecStart=${LLM_HOME}/bin/cuda/llama-server -m ${LLM_HOME}/models/qwen36-mtp/Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf \
  --mmproj ${LLM_HOME}/models/qwen36/mmproj-F16.gguf --no-mmproj-offload \
  --host 127.0.0.1 --port 8093 -ngl 99 -fa on -c 65536 -np 2 -ctk q8_0 -ctv q8_0 \
  --spec-type draft-mtp --image-max-tokens 2048 --sleep-idle-seconds 1800
Restart=on-failure
[Install]
WantedBy=default.target

Notes on the fast tier:

  • Vision encoder on the CPU: --no-mmproj-offload is required on 16 GB. With the MTP head on the GPU, the vision encoder runs out of memory at any context size. On the CPU an image still takes about 9 s.
  • Context: 2 slots × 32K covers about 99% of real prompts. Route bigger prompts to the AMD tier.

Best tier, AMD iGPU (shares system RAM): same model family at Q4.

[Service]
Environment=LLM_HOME=/opt/llm

5. Find your own offload point for a big MoE#

Sweep --n-cpu-moe, then keep the lowest value that loads:

for n in 99 46 44 42 40; do
  LD_LIBRARY_PATH=$LLM_HOME/bin/cuda $LLM_HOME/bin/cuda/llama-bench -m MODEL.gguf -ngl 99 -ncmoe $n \
    -fa 1 -ctk q8_0 -ctv q8_0 -ub 2048 -b 2048 -p 4096 -n 32 -r 1 -o md || echo "ncmoe=$n OOM"
done

Bigger -ub and -b values (2048) raised prompt speed 2.7× when the experts live in RAM.

6. Colibri (only if you have lots of RAM and fast or multiple NVMe drives)#

git clone --depth 1 --branch v2.0.0 https://github.com/JustVugg/colibri && cd colibri/c
make -j16 colibri ARCH=native && cp colibri colibri-cpu                                   # CPU
make clean && make -j16 colibri CUDA=1 CUDA_ARCH=sm_120 CUDA_HOME=/usr/local/cuda ARCH=native && cp colibri colibri-cuda   # CUDA 13 toolkit from step 1
make clean && make -j16 colibri VK=1 ARCH=native && cp colibri colibri-vk               # Vulkan (needs libvulkan-dev + glslc)
ln -sf colibri-cuda colibri                                                              # the variant `coli` will run
cd .. && ./start-here.sh --model glm-5.2 --yes --backend cpu --dir <models dir>   # 429 GB download
# start-here.sh auto-starts a server on :8000 when the download finishes; stop it before running your own service

With 60 GB RAM and one NVMe, expect about 0.3 tok/s for GLM-5.2, and a prefill too slow for prompts over about 2K tokens.

7. Wire it into Claude Code (or any agent)#

  • Router: an OpenAI-compatible router with per-role backend lists (chat, vision, embed, deep). It takes the first healthy backend with an idle slot (/health, /slots), and a max_prompt per backend sends large prompts to the bigger-context tier.
  • MCP server: a small stdio server exposing a few tools:
  • local_ask (it reads files or a git diff itself, so file contents never enter Claude's context)
  • local_vision (screenshot triage)
  • local_search (embeddings fused with a code map)
  • status

Register it with claude mcp add -s user local-llm -- python3 <server.py>. - Smoke-test before reconnecting: send initialize and tools/list over stdio first. A syntax error makes /mcp reconnect fail with only "connection closed". - Delegation rules in the global CLAUDE.md: send bulk, low-stakes, verifiable work to local models (extraction, first-pass diff review, drafts, screenshot triage). Keep decisions, subtle bugs and security with Claude, and verify what local models claim.
